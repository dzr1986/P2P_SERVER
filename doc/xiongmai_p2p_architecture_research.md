# 雄迈 P2P 公开资料续查与自研架构参考

> 检索日期：2026-09-30。目标：自建设备接入、按设备 ID 访问、直连与中继服务，获得类似雄迈的使用体验。
> 本文整理公开资料并提出独立设计，不修改业务代码、不测试真实设备、不下载或运行第三方 SDK 二进制。

## 1. 先明确：仿造能力，不等于兼容雄迈私有协议

**建议先做独立 P2P 平台，而不是把接入雄迈现有设备作为第一阶段的前提。**

| 目标 | 所需条件 | 本次资料是否足够 |
| --- | --- | --- |
| 自己的设备与 App 按 ID 建立连接，直连不通时中继 | 自有身份与授权系统、信令、穿透/中继、加密会话和 SDK | 足以形成架构及验证方案，但仍需实现和实测 |
| 使用雄迈 SDK 访问雄迈设备，再桥接到自己的播放器 | 合法取得且匹配设备的 SDK、设备访问权限、平台接入条件 | 有 API 文档和第三方调用示例，不保证具体设备兼容 |
| 不依赖雄迈 SDK，让现有雄迈设备直接连接自己的云 | 可追溯的私有协议、设备配置/固件支持、鉴权和服务发现规则 | **不足**：未确认完整注册、打洞、中继线格式及认证机制 |

全文采用三种证据标记：

- **【XM 文档】**：雄迈开放平台公开仓库的接口说明，证明相应版本的 API 语义。
- **【标准/开源】**：独立标准或开源实现，不代表雄迈内部也采用它。
- **【自研建议】**：为本项目目标提出的设计，不是对雄迈实现或本仓库现状的认定。

上次 `LISTWIFIAP` 调查的边界不变：TUTK 的 `0x0340/0x0341` 和 4 字节请求，不能证明用户所述雄迈 `0x0201 + 8 字节` 的响应。Wi-Fi 配置命令也不是搭建 P2P 基础设施必须先解决的问题。

## 2. 本次新增的雄迈公开证据

以下引用固定到 `xmeye/openplatform-docs` 的提交 `7db946442bb3254402f9f20e16baba97a85e4b56`。文档代表历史接口说明，不代表所有产品或当前 SDK 的统一行为。

### 2.1 三种访问模式，不能与直连/中继混为一谈

**【XM 文档】** Android 集成指南区分：[X1]

| 模式 | 文档中的含义 | 不能推导出的结论 |
| --- | --- | --- |
| AP 模式 | 手机连接设备自身热点 | 不等于互联网 P2P |
| 本地模式 `SysInitLocal` | 不要求注册平台用户；可按序列号，或 IP + 端口访问；明确支持远程设备 | **“本地登录”不等于只走局域网，也不等于完全不使用服务器** |
| 用户模式 | 通过平台用户体系维护关联设备列表 | 登录平台成功不等于已经与设备建立媒体连接 |

**【自研建议】** 分开建模“用户是否登录”“使用什么设备地址”“底层选中了什么路径”。不要用一个 `isLocal` 同时表达三个概念。

### 2.2 云登录确实有公开接口，但没有随接口公开握手格式

**【XM 文档】** `H264_DVR_Login_Cloud` 接口将地址参数解释为设备序列号；文档说明该客户云接口需要在雄迈服务器注册。成功返回设备句柄，失败返回零。[X2]（136–146 行）

这证明“序列号 → SDK 云登录 → 设备句柄”的 API 链路，**不能证明**设备注册报文字段、NAT 协调端口、鉴权密钥算法或中继帧格式。

旧文档还存在不同登录接口的 `socketType` 数值说明不一致的问题；不能把某一接口的参数值当作通用云协议常量。

### 2.3 在线查询与设备登录是独立操作

**【XM 文档】** `SysGetDevState` 可以在未登录设备时按序列号查询在线状态；设备功能操作需先 `DevLogin`，结束访问用 `DevLogout`。[X1]（112–133 行）

另一份 FAQ 说明，批量查询会逐台回调；状态回调的 `param1 > 0` 表示在线，`param1 == 0` 表示离线。不要将未解释的负值也直接归类为离线。[X4]（75–81 行）

**【自研建议】** 提供独立的：

1. 身份与权限验证；
2. presence（最近是否在线）；
3. 会话建立；
4. 媒体可用性检查。

“在线”只能作为连接线索，不能当作鉴权成功或必然能出图的保证。

### 2.4 在线状态可能滞后，不是瞬时真值

**【XM 文档】** FAQ 将断电后三分钟内状态变成离线描述为正常，并要求 App 刷新状态。[X5]（11–25 行）

**不能据此推导雄迈心跳周期为三分钟**：文档没有公开心跳、租约、查询缓存和 UI 刷新的各自时序。

**【自研建议】** 返回 `last_seen`、状态更新时间和未知/过期状态；让 UI 区分“最近在线”“正在连接”“当前可播放”。

### 2.5 公开资料提到 DSS 转发，但未说明自动降级策略

**【XM 文档】**

- 平台 FAQ 将服务器报警推送、DSS 转发列为需要用户体系支持的功能。[X5]
- 另一份 FAQ 指出高清转发需要 DSS 设备/DSS 固件。[X4]

这些文字证明相关产品存在转发能力及接入条件，**没有证明**：

- 所有雄迈设备均可转发；
- 直连失败后何时、按什么规则切到转发；
- DSS 就是 TURN，或其承载方式一定是某一种 TCP/UDP 格式。

**【自研建议】** 给中继能力、用户权限、带宽配额和设备能力分别建模，不要把中继当成无限制的免费兜底。

### 2.6 低功耗设备需要独立唤醒流程

**【XM 文档】** 门铃等设备先调用 `DevWakeUp`，等待回调后再登录或打开视频；`msg.arg1 >= 0` 表示唤醒成功，负值表示失败。允许休眠时退出设备登录；设备在没有客户端连接的情况下自动休眠。[X5]（28–51 行）

这**不是**唤醒传输协议，也不意味着离线、掉电、无网的设备都能唤醒。一个观看者退出时，其他观看者可能仍维持连接。

**【自研建议】** 唤醒请求做权限检查、合并与限频；区分休眠、掉线和掉电。设备若关闭所有网络接收能力，需要额外的低功耗网络通道或网关才能被远程唤醒。

### 2.7 断线回调与主动退出不同

**【XM 文档】** NetSDK 初始化可设置断线回调；主动调用 `H264_DVR_Logout` 关闭连接不触发该断线通知。[X2]（25–46 行）

**【自研建议】** 区分主动退出、鉴权失败、路径失效、设备重启和服务端维护。主动退出不应被自动重连逻辑重新拉起。文档未给出自动重连退避算法，不能照猜。

### 2.8 可设置服务器地址，不等于可以替换整套雄迈云

**【XM 文档】** `SysSetServerIPPort` 的说明针对非默认的**账户服务器**地址和端口。[X3]（115–129 行）

未见该接口承诺更换 NAT 协调服务器、中继、设备发现和鉴权体系。不能仅凭它就认定现有雄迈 SDK 可以接入任意自建 P2P 服务。

## 3. 值得继续追踪的公开项目

### 3.1 新发现：`wire67/xmeye_cloud_to_rtsp`

**【第三方开源调用示例】** 核查提交 `344ce6be2e5516fc2849fe2336b546fba3486e45` 的 README 及 Python 实现。[O1]

实际代码通过 `NetSdk.dll` 调用 `H264_DVR_Login_Cloud`、`H264_DVR_RealPlay`、`H264_DVR_SetRealDataCallBack_V2`，并在退出时登出。它是 **SDK 桥接器，不是开源雄迈 P2P 协议栈**。

可借鉴的工程分层是“云连接 → SDK 帧回调 → 有界队列 → 独立媒体输出”。慢播放器不能阻塞网络回调；但丢弃压缩视频时应按帧与解码依赖处理，不能把任意丢字节作为通用办法。

README 包含作者在特定 DLL/设备上的故障和抓包结论，本次没有复现实验，**不采纳其旧 DLL 降级建议作为通用结论**。也未运行其随仓库分发的程序。名称含 RTSP，不代表底层云传输就是 RTSP。

### 3.2 之前资料仍有价值，但用途不同

- **雄迈 NetSDK/XNetSDK 下载索引**：继续获取可追溯官方接口资料的入口；下载页有历史包链接，不代表包内容或当前可用性已核实。[X6]
- **`hifided/IPCAS`**：理解云登录后如何使用录像 API；它仍依赖 SDK 二进制，不是 NAT 服务端实现。[O2]
- **`OpenIPC/python-dvr`**：DVRIP/NetSurveillance/Sofia 设备控制及历史文档索引；不能用设备侧 TCP 控制协议替代云注册、打洞与中继协议。[O3]

## 4. 自研平台的推荐边界

以下全部是 **【自研建议】**，不是雄迈实际部署拓扑，也不声称本仓库已经实现。

### 4.1 逻辑组件

```text
设备 SDK ──认证连接──┐
                   ├── 接入/信令服务 ── 在线租约与会话路由
App SDK ──认证连接──┘          │
                       身份、绑定、访问授权

设备 SDK <──── 经验证的端到端直连路径 ────> App SDK
    │                                         │
    └────── 经 TURN/中继转发的加密路径 ─────────┘

STUN/TURN：供端点收集候选地址、验证可达性和取得中继资源
监控/计费：观察连接阶段、路径、流量、错误与资源使用
```

| 组件 | 责任 | 不应承担的责任 |
| --- | --- | --- |
| 设备身份与绑定 | 唯一身份、设备密钥、公钥绑定、所有权及共享授权 | 仅凭知道设备 ID 就放行 |
| 接入与 presence | 已认证的设备在线租约、会话所在节点、重连 | 存储明文视频、长期替媒体转发 |
| 信令/协调 | 转发连接邀请、能力及候选地址、取消与错误 | 将客户端声称的公网地址直接当作可信事实 |
| STUN | 帮助端点观察映射地址，支持连接检查 | 账户管理、保证穿透成功 |
| TURN/中继 | 有配额、有时限地转发流量 | 无鉴权的任意地址代理 |
| SDK 会话层 | 路径选择、端点认证、加密、多路业务及生命周期 | 把云登录、直连与出图合成一个布尔值 |
| 媒体层 | 编解码适配、帧与时间戳、拥塞和缓冲、播放 | 将媒体解析规则固化进设备注册协议 |

初期可合并部署部分逻辑服务，但保持接口和安全边界。账户、presence 与媒体的扩容依据不同，不应让所有媒体流经同一台信令服务。

### 4.2 一次观看连接的完整流程

1. **设备上线**：设备验证服务器身份，用自身凭据建立受保护的出站连接，登记短期在线租约及能力。
2. **访问授权**：App 验证用户身份与设备访问权。设备 ID 是定位信息，不是密码；分享权限应可撤销。
3. **查询与唤醒**：查询 presence；休眠设备走受控唤醒，等待结果。查询结果仅供参考，连接仍可能失败。
4. **会话邀请**：签发有时效、限定设备与请求方的授权，创建唯一会话 ID；设备接受后进行候选与能力协商。
5. **地址收集与检查**：收集局域网、IPv4/IPv6、公网映射和中继候选，通过已认证信令交换；由 ICE 检查候选对。
6. **选路**：在策略与可达性允许时优先直连；需要时使用中继。为减少首屏等待，可提前收集中继候选，而非所有直连超时后才开始准备中继。
7. **端到端认证与加密**：校验对端身份及授权；即使走中继也保持端到端保护。设备长期公钥或证书绑定应通过可信流程核对，不能只信任未经约束的信令指纹。
8. **业务建立**：分别打开控制、音视频、录像下载通道，协商编码格式；只有收到并解码出可用媒体才报告首帧成功。
9. **恢复与释放**：网络切换后重新验证路径，必要时 ICE restart；退出时取消未完成邀请、释放媒体和中继资源，最后关闭或归还会话。

标准 ICE 的候选收集、检查、提名、重启可参考 RFC 8445；**ICE 假设信令连接已经存在，并不替你实现账户与设备授权**。[R1]
切换路径应使用所选协议栈支持的机制；不要假设 RFC 8445 在选路完成后会自动任意切换到另一个候选。重启会更新 ICE 凭据。

### 4.3 三套状态，不要只保留 ONLINE/OFFLINE

| 层 | 建议状态 | 重要区别 |
| --- | --- | --- |
| 设备 presence | 未知、在线、疑似过期、离线、休眠 | 最近在线不保证现在可达；休眠需能力依据 |
| 连接会话 | 授权中、邀请中、检查路径、端点认证、已连接、恢复中、已关闭 | 已连接时另外记录 direct/relay 及实际 transport |
| 媒体 | 未启动、等关键帧、播放中、停滞、已停止 | 信令成功或 UDP 可达不等于视频已经可播放 |

每阶段都应有独立错误码、取消和截止条件。接收迟到的成功回调时，要用会话 ID/代次识别已经取消的请求，避免误恢复旧会话。

## 5. 哪些协议应该自定，哪些应复用

### 5.1 建议自定业务控制面，不重写基础传输

下面是概念级接口职责，**不是雄迈命令号，也不是最终报文定义**：

| 操作 | 最低语义 |
| --- | --- |
| 设备注册/续租 | 已认证设备身份、启动代次、能力、租约及路由节点 |
| 在线查询 | 经过授权的目标集合、状态更新时间、未知/过期处理 |
| 建立/取消会话 | 请求 ID、目标、请求者身份、权限范围、截止时间、幂等取消 |
| 会话协商 | 版本、能力、候选、ICE 代次、端点身份绑定；秘密不进入日志 |
| 中继资源申请 | 经授权的会话、短期凭据、配额、资源释放条件 |
| 唤醒/释放 | 唤醒能力、合并重复请求、结果回调、活动观看者计数 |
| 错误/观测 | 阶段、可重试性、关联 ID；不向未授权请求泄露设备存在性 |

控制消息应有长度上限、版本与未知字段策略、鉴权覆盖范围和重放防护。对重试使用请求 ID 去重；不要仅靠时间戳抵抗重放，也不要复用设备 ID 作为连接 ID。

### 5.2 STUN、ICE、TURN 各自做什么

**【标准/开源】**

- **STUN**：观察映射地址/进行检查；一个映射地址并不能证明其他目的地可按同样方式到达。
- **ICE**：交换多种候选并实际检查候选对，不需要先用一个“对称 NAT/锥形 NAT”标签决定全部结果。[R1]
- **TURN**：分配中继地址，维护 allocation、permission、channel 等状态及其续期；不是收包后任意转发的无状态代理。[R2]
- **TLS 到中继不等于端到端加密**：TURN 规范明确指出，要求端到端安全的应用应在端点间加密数据。[R2]（§3.4）

不要承诺固定穿透率。CGNAT、多层 NAT、IPv6 防火墙、VPN 和运营商策略应以真实网络检查结果分类，而非只依据路由器型号。

### 5.3 UDP 完全被禁时，仅增加 UDP 中继没有用

RFC 8656 区分“客户端 → TURN”与“TURN → peer”两段：前者可以使用 UDP、TCP、TLS-over-TCP 等；该规范的 UDP allocation 在服务器到 peer 一段仍使用 UDP。TCP relay 是另一个扩展，不能混称。[R2]（§3.1）

**【自研建议】**

- 验证 SDK **客户端侧**确实支持到 TURN 的 TCP/TLS，而不只是服务器支持。
- 两端均不能向公网发送 UDP 时，要验证两端各自通过受支持的中继接入方式形成可用路径，包括必要的 relay-to-relay 候选对。
- 可以评估在许可网络策略下提供 TLS 中继入口；使用 443 端口也不意味着它是 HTTPS，更不保证企业代理放行。
- 走 TCP 承载时要评估队头阻塞、带宽与实时性；不能把“可连接”当成“可流畅播放”。

### 5.4 可评估的组件组合

| 路线 | 适合目标 | 仍需自己解决 |
| --- | --- | --- |
| WebRTC + 自有信令 + coturn | App/浏览器观看、控制与媒体并存 | 设备身份、绑定授权、编码兼容、资源限制、运营 |
| libdatachannel + 合适的 ICE 后端 + coturn | C/C++ 原生设备与浏览器/原生端互通 | 媒体生产/消费、业务协议、跨平台构建与授权、后端功能实测 |
| libjuice + 成熟的端到端安全/业务传输层 | 较轻量的原生端 UDP 连接 | 不能把 ICE 库当成加密媒体或可靠消息协议；需补齐相应层 |
| 全自研穿透、可靠 UDP、中继和密码协议 | 只有明确不能采用现成栈时才考虑 | 重传、拥塞、MTU、重放、路径迁移、跨版本互通等全部责任 |

核实到的实现边界：

- libdatachannel README 列明 DataChannel 使用 SCTP、媒体使用 SRTP，底层结合 DTLS、ICE、STUN/TURN；它还需外部信令交换描述与候选。[O5]
- libjuice 的该提交 README 在功能列表中提到 TCP candidates，同时在限制中写明 **Only UDP**；这不足以证明其客户端具备完整 TCP/TLS TURN 回退。必须核查目标版本的 API、实现及实测，不能由文档中的“TURN 支持”一词推定。[O4]
- coturn README 明确区分客户端到服务器支持的 UDP/TCP/TLS 等承载，并提供限时认证、配额与带宽控制。[O6]

**推荐起点是第一或第二条路线**。若只要求自有原生端，可以评估第三条；若“UDP 封锁仍可用”是验收条件，就不能在缺少客户端 TCP/TLS 回退证据时完成选型。

## 6. 生产化时不能省略的设计

以下是 **【自研建议】**，不是对当前仓库的代码审计或已完成功能清单。

### 6.1 身份、授权与中继滥用防护

- 每台设备独立凭据；设备 ID 可展示，但不能替代持有密钥的证明。设备绑定/转让/恢复出厂需要独立流程。
- 用户登录平台、被允许访问设备、端点确认对方身份是三次不同检查。共享权限应限制设备、动作及有效期。
- 中继默认拒绝匿名使用，限制每用户/设备/租户的 allocation 数、速率、并发和总带宽。coturn 有 `user-quota`、`total-quota`、`max-bps` 等设置；不要误把配额数值为零理解成禁止使用。[O7]
- 限时 TURN 凭据由可信服务端签发，签发密钥不下发 App/设备。限时凭据本身不自动实现“只允许访问某台设备”的业务 ACL，也不保证到期瞬间切断已有会话，需另行定义撤销与资源策略。
- 限制中继访问自身管理网、回环、多播及云元数据地址，避免成为内网代理；公网 TURN 的地址限制与端点在授权会话中使用局域网候选不是同一回事。[O7]
- 拒绝超长消息、异常候选数量与未授权会话；限制未验证源地址的响应量，避免放大。
- 对日志中的凭据、ICE 密码、设备标识及地址做最小化处理；媒体、抓包和诊断材料单独授权与保留。

### 6.2 不同的保活不能互相代替

至少分清：

1. 设备对接入服务的在线租约；
2. 选定数据路径的 NAT 保活与可达性/发送同意检查；
3. TURN allocation、permission、channel 的维护；
4. 业务无操作超时与低功耗休眠条件。

控制连接还活着不意味着视频路径还活着；持续发送视频也不代表所有 TURN 状态都会自行续期。按协议栈处理这些状态，不用一个定时器包办。[R1]（§11）、[R2]（§3.2–3.5）

### 6.3 多观看者、网络变化与集群

- 设备重启、重连和路由接管使用启动代次/租约版本，拒绝旧连接覆盖新在线信息。
- 新连接按容量与区域分配节点；已建立会话保持路由粘性。中继维护/故障可能需要重新分配资源，不能假定换一个 DNS 地址就能迁移正在传的视频。
- 信令集群至少能定位设备所在连接节点；账户持久数据与高频 presence 分离，避免每次心跳都写核心业务表。
- 网络从 Wi-Fi 切到蜂窝时重新验证候选；应用重连使用指数退避与抖动，区分鉴权失败和瞬时网络失败。
- 多观看者可能使设备上行重复发送多路媒体；是否引入媒体分发服务应按带宽、权限及端到端加密信任边界决定。
- 录像下载不应挤占直播；使用独立队列、优先级和有界缓存，慢消费者不能导致无限积压。

### 6.4 容量计算应基于观看会话，而不是设备总数

以下仅是**假设示例**，不是雄迈参数或性能数据：

- 在线设备数为 `N`，业务在线续租间隔为 `H` 秒，则稳态续租请求量约 `N / H` 次/秒，另计响应、抖动和重连峰值。它不用于设定 ICE/TURN 的协议定时器。
- 同时观看会话数 `V`，其中比例 `r` 经一个中继转发，每路设备到观看者的平均码率为 `b`，则该单跳模型下中继视频出口约为 `V × r × b`，入口约同量。
- 例如 `V=1000`、`r=20%`、`b=2 Mbit/s`，视频出口约 `400 Mbit/s`，入口也约 `400 Mbit/s`，未计包头、重传、音频和冗余。
- 双中继路径增加服务器间流量；多区域、上下行对讲、多观看者及链路计费口径需另算。端口、文件描述符、包速率和握手 CPU 也可能先耗尽。

## 7. 分阶段验证与验收清单

**【自研建议】** 每阶段交付可复现的测试证据，不用“支持 P2P”一句话验收。

| 阶段 | 交付范围 | 必须验证 |
| --- | --- | --- |
| A：身份与信令 | 注册、绑定授权、presence、邀请/取消 | 未授权查询/连接被拒；重复、过期、乱序请求不产生幽灵会话 |
| B：标准穿透 | 候选交换、直连及强制中继 | 同 LAN、不同 NAT、多层 NAT、IPv4/IPv6、无 hairpin 场景 |
| C：受限网络与恢复 | 客户端到中继的 TCP/TLS、路径恢复 | 单端/双端 UDP 封锁、网络切换、接入服务或中继重启；不能把失败测试隐藏成“网络问题” |
| D：媒体与业务 | 首帧、控制、对讲、录像及多观看者 | 丢包/乱序/抖动、弱带宽、慢消费者、关键帧恢复、长时间资源释放 |
| E：运营与低功耗 | 配额、监控、唤醒、休眠及撤销 | 配额耗尽、凭据过期、撤销中会话、唤醒重复请求和最后一个观看者退出 |

至少记录：

- 连接尝试总数及各阶段成功率；直连率、中继率的分母要一致；
- 授权、信令、路径、端点认证与首帧的独立耗时分布；
- relay 的实际客户端 transport，避免把 TCP/TLS 回退误统计成 UDP 直连；
- RTT、丢包、吞吐、排队长度、首帧/冻结、CPU/内存与中继进出流量；
- 失败阶段与可重试性；区分权限、离线、不可达、中继资源不足和编解码不兼容。

这些是后续实现的验收要求；**本次文档任务没有执行这些网络或负载测试**。
