> 目标：把本项目从「P2P 打洞 + 中继」底座，演进为行业一流的 P2P 流媒体传输栈。
> 本文回答三个问题：要学什么、向哪些开源项目学、按什么顺序落地。
> 第二轮已落地项见文末，与 `代码优化分析报告.md` 对应。
> 行业 P2P 模型（DERP / DCUtR / WHIP / MoQ / 28181）与阶段规划见
> [`P2P模型图谱.md`](P2P模型图谱.md)、[`P2P服务器开发计划书.md`](P2P服务器开发计划书.md)（档 B 现网 / 档 C 旁路）。

## 1. 能力地图：流媒体传输栈缺什么

一条能扛住公网直播/通话的 P2P 链路，在打洞成功之后还需要六层能力：

```
┌────────────────────────────────────────────────────────┐
│ 6. 业务自适应   码率自适应(ABR)、simulcast/SVC 分层订阅  │
│ 5. 拥塞控制     GCC / BBR / SRT LiveCC，pacing 平滑发送  │
│ 4. 抗丢包       ARQ(NACK/快速重传) + FEC + 交织，按需组合 │
│ 3. 时序恢复     jitter buffer、播放时钟、延迟预算管理     │
│ 2. 可靠传输核   自适应 RTO、滑动窗口、乱序重组（本项目 Session）│
│ 1. 连接底座     ICE 打洞、中继兜底、加密（第一轮已完成）   │
└────────────────────────────────────────────────────────┘
```

当前项目已有第 1、2 层的骨架，第二轮补齐了第 2 层的现代化（自适应 RTO/快速重传/拥塞窗口）
和第 4 层的入门（XOR FEC + 丢包统计）。第 3、5、6 层是后续主战场。

## 2. 该学的开源项目（按主题映射）

### 2.1 低延迟可靠传输（ARQ）—— 首选学习对象

| 项目 | 语言 | 学什么 |
|------|------|--------|
| [skywind3000/kcp](https://github.com/skywind3000/kcp) | C（2 个文件） | **最值得逐行精读**。自适应 RTO、快速重传（跨越次数触发）、`nodelay` 模式、cwnd/ssthresh 拥塞控制、流模式合包。本项目 Session 的升级即对标 ikcp.c |
| [xtaci/kcp-go](https://github.com/xtaci/kcp-go) | Go | KCP 之上的工程化：**Reed-Solomon FEC**（数据/校验分片可配比）、pacing、缓冲池零分配、smux 多路复用 |
| TCP RFC 6298 / 5681 | 规范 | RTO 计算（SRTT/RTTVAR/Karn）与拥塞控制（慢启动/快速重传/快速恢复）的权威定义，代码量小，必读 |

### 2.2 直播级传输协议

| 项目 | 语言 | 学什么 |
|------|------|--------|
| [Haivision/srt](https://github.com/Haivision/srt) | C++ | **直播传输标杆**。固定延迟预算（latency budget）下 ARQ+FEC 组合、too-late-packet-drop（过期帧不再重传，直播关键）、双向带宽估计、AES 加密集成 |
| [quic-go](https://github.com/quic-go/quic-go) / [quiche](https://github.com/cloudflare/quiche) | Go/Rust | QUIC：0-RTT、多流免队头阻塞、datagram 扩展（RFC 9221）。**Media over QUIC (MoQ)** 是下一代方向 |

### 2.3 WebRTC 生态（实时音视频事实标准）

| [pion/webrtc](https://github.com/pion/webrtc) | Go | 可读性最好的完整 WebRTC 栈。`pion/interceptor` 里的 NACK/TWCC/GCC 实现清晰独立，适合移植思路 |
| [versatica/mediasoup](https://github.com/versatica/mediasoup) | C++ | SFU 架构、**发送端带宽估计 + 空间/时间分层分配算法**、simulcast/SVC 路由。C++ worker 与本项目技术栈一致 |
| [livekit/livekit](https://github.com/livekit/livekit) | Go | 生产级 SFU 工程化：selective subscription、speaker detection、多区域分布式 |

| [paullouisageneau/libdatachannel](https://github.com/paullouisageneau/libdatachannel) | C++ | 与本项目已用的 libjuice 同作者；ICE+DTLS+SCTP 的轻量组合，P2P datachannel 参考 |

## 3. 学习与落地顺序建议

1. **精读 ikcp.c（~1500 行）**：对照本项目 `Session.h` 第二轮改动，理解每个机制为什么这样设计（已完成对标：自适应 RTO、快速重传、cwnd）。
2. **精读 SRT RFC 草案第 4、5 章**：latency budget 与 too-late-packet-drop 是直播传输的灵魂，下一步应在 Session 不可靠通道上实现「帧过期丢弃 + 固定播放延迟」。
3. **读 pion/interceptor 的 GCC/TWCC**：把 `LinkStats`（本轮新增）喂给一个简化版 delay-based 带宽估计器，输出目标码率回调给应用层。
4. **读 kcp-go 的 Reed-Solomon FEC**：把本轮的 XOR FEC（单帧恢复）升级为 RS(k,n) 多帧恢复，引入 [klauspost/reedsolomon](https://github.com/klauspost/reedsolomon) 的 C++ 等价实现或自研 GF(2^8) 编解码（common/Crypto.cpp 已有 GF 表基础）。
5. **读 mediasoup 的 simulcast 分配算法**：多订阅者场景下按下行带宽选层。
6. **验证方法**：用 `tc netem` 模拟丢包/延迟/抖动（`test.sh` 可扩展），指标看 P50/P99 端到端延迟、卡顿率、带宽利用率。

## 4. 第二轮已落地（本仓库）

对标 KCP / SRT / WebRTC，`client/sdk/session/Session.h` 完成以下升级（单测 `tests/session_test.cpp`）：

| 特性 | 对标 | 说明 |
|------|------|------|
| 自适应 RTO | TCP RFC 6298 / KCP | SRTT/RTTVAR 平滑估计，Karn 算法排除重传帧；累计 ACK 批次取最小样本，避免被队首阻塞帧污染；超时退避 1.5x（KCP 风格） |
| 快速重传 | RFC 5681 / KCP fastresend | 3 次重复累计 ACK 立即重传队首帧，不等 RTO；快速恢复窗口减半不归零 |
| 拥塞窗口 | RFC 5681 / KCP cwnd | 慢启动指数增窗 → 拥塞避免每 RTT +1；超时回退 cwnd=2、ssthresh=inflight/2；`send()` 返回 -2 即上层降码率信号 |
| 不可靠通道 seq | RTP 序号 | 不可靠帧带独立序号，接收端估计丢包率（seq 空洞） |
| XOR FEC | SRT/flexfec 入门形态 | 每 4 帧发 1 个 XOR 校验帧（TT_FEC），单帧丢失免重传恢复；低速流 100ms 部分组冲刷；迟到重复帧去重 |
| LinkStats | WebRTC getStats | srtt/rttvar/rto/cwnd/inflight/重传/FEC/丢包统计，`P2PClient::link_stats()` 暴露，供自适应码率 |

## 5. 后续路线（第三轮候选）

- **延迟预算 + too-late-drop**（学 SRT）：不可靠通道帧带时间戳，超过播放延迟预算的帧不再投递/重传
- **完整 GCC / TWCC**（学 pion/interceptor）：`TwccEstimate.h` 已落地一维 Kalman +
  `TT_TWCC` 到达反馈；`AbrController` 与 delay-based 目标按 2:1 混合。完整 RTCP/TWCC
  与 GCC overuse detector 状态机仍可再对齐 pion
- **RS-FEC**（学 kcp-go）：GF(2^8) Reed-Solomon，支持组内多帧丢失恢复，比例可按丢包率自适应
- **pacing**（学 WebRTC pacer / kcp-go）：令牌桶平滑突发，避免瞬时排队丢包
- **jitter buffer**（学 NetEQ）：接收端播放缓冲与时钟恢复，SDK 提供「按时间戳出帧」API
- **多路径**（学 iroh / MPTCP）：直连 + 中继同时探测，按 RTT/丢包动态切换或聚合
- **ICE restart / TURN-over-443**：已落地，见 [`P2P穿透与流媒体实践.md`](P2P穿透与流媒体实践.md)

LAN 组播发现已落地（`MSG_LAN_QUERY/ANNOUNCE` + `IOTC_Search_Device`）。

## 6. 穿透层对照（2025–2026 实践，已部分落地）

行业共识：ICE 编排 STUN（地址发现）+ 打洞 + TURN（兜底）；生产上 **15–30% 会话走中继**。
一对一 IPC 预览适合 P2P；一对多直播应走推流+CDN，不要 mesh。

| 实践 | 本仓库落地 |
|------|------------|
| Offer/Answer 定 ICE 角色，避免双方 controlling | CONNECT_OK 后发起方 `gather`；被邀方先 `set_remote`；`IceSdpMsg.src_uuid` 认领 |
| 嵌入 STUN，收集 srflx | NatServer 应答 RFC 8489 Binding（`StunBind.h`）；公网 juice 指向 NatServer，回环跳过以免 23s STUN 拖死直连 |
| Trickle ICE，勿过早 gathering done | 首包 host SDP 只 `set_remote`；完整 SDP 再 trickle；`tick_ice` 兜底 |
| ICE `user_ptr` 稳定 | `conns_` 存 `unique_ptr<Conn>`，扩容不移动回调对象 |
| 跨服 SDP 不丢 | 本地无 `dst_uuid` 时 `MSG_ICE_SDP` 经 sync 转发；HMAC 剥掉再投递 |
| 区域化 TURN | `Region` / `pick_proxy` 同区加权；`QuotaMB` 计量 |
| 中继后继续打洞、切回直连 | `tick_connections` 后台打洞，`direct_ok` 后改 `juice_send` |
| ICE restart（换网换 ufrag） | `restart_ice` 重建 agent，`juice_prev` 扛媒体；对端认 ufrag 变化 |
| TURN-over-443 | Proxy `AltPort` 兼听；`ProxyAltPort` 写入 CONNECT 候选 |
| DERP TCP/TLS 先通再切 | Proxy `TcpPort` + `ProxyTcpPort`；客户端 `-tcp`；`direct_ok` 切 `juice_send` |
| TWCC + Kalman | `TT_TWCC` 反馈 + `DelayKalman`；`avSuggestedBitrateKbps` 混合 |

详细映射与待办见 [`P2P穿透与流媒体实践.md`](P2P穿透与流媒体实践.md)。
